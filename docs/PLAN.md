# PLAN

*The build plan: vision and non-goals, the requirement capabilities, the eight frozen seams, the milestone roadmap and its gates, the risk register, and the definition of done for v1.0. Date: 2026-09-17. Status: accepted spine; the specification documents are written against this file, `ARCHITECTURE.md` and `DECISIONS.md`. Every example in these documents is synthetic or a published third-party worked example. Nothing here describes any real household.*

**Reading order.** The set is eight documents. Read in this order: **[PLAN.md](PLAN.md)** (what and when) → **[ARCHITECTURE.md](ARCHITECTURE.md)** (how it is built: stack, crate graph, engine API, request flow, extension points, build and release pipeline) → **[DECISIONS.md](DECISIONS.md)** (why, as architecture decision records, with the corrections of record and the open decisions) → then the five specifications, each written against that spine: **[DOMAIN-MODEL.md](DOMAIN-MODEL.md)** (the plan-file schema and domain model), **[ENGINE-SPEC.md](ENGINE-SPEC.md)** (the ledger, tax and decision engines), **[SIMULATION-SPEC.md](SIMULATION-SPEC.md)** (the stochastic and retirement layer), **[SECURITY.md](SECURITY.md)** (threat model, container, transport, repository hygiene) and **[TESTING.md](TESTING.md)** (the validation corpus and gates). Where a specification and the spine disagree, the spine wins and the disagreement is a defect in the specification.

**Terminology used throughout (standing definition).** "The binary" or "the release" always means one thing: a **local web application for macOS**, shipped as a single self-contained executable (universal: Apple Silicon + Intel). Launching it starts a web server bound to loopback, serves the embedded web app over TLS, and opens the default browser. The user interface is a web app in the browser. It is not a native desktop GUI and not an Electron/Tauri window, and nothing else has to be installed.

Two corollaries are part of the definition. (1) The optional `.app` wrapper described under M0 is a **notarization container and Finder launcher around the byte-identical executable**: `Info.plist` with `LSUIElement`, an icon, the same Mach-O. It has no second executable, no bundled runtime, no WebView, no native window and no Dock icon. It is packaging; it is never licence to add a native shell. (2) Tauri v2 is **refused**, along with Electron, any WebView host and any browser-side WASM engine.

## 1. Vision and non-goals

### 1.1 Vision

A general-purpose, self-hosted personal financial **planning** application for US households of one or two people. It answers forward-looking questions and shows its work:

1. **Where does the next dollar go this year, and why?** One auditable, after-tax, risk-matched return figure (`r_u`) per option across 401(k)/403(b), Roth vs Traditional, IRA, backdoor and mega-backdoor Roth, HSA, 529, taxable investing and debt prepayment.
2. **What does the household's year-by-year cash flow and exact federal tax look like to the end of the plan**, under a baseline ("Current Course") and under alternatives expressed as diffs?
3. **Is it enough, and what happens if it is not?** A scorecard (funded ratio, horizon-appropriate fail-safe rate, success probability always paired with the size and timing of the cut, dollar guardrails). Never a lone probability.

The durable asset is that **the numbers are right and can be shown to be right**: every figure on screen resolves to named worksheet lines, sourced and versioned parameters, a named rounding rule, and a result pin. The differentiator (the next-dollar engine) is original work with no external oracle, so the layers beneath it (money arithmetic, tax function, ledger conservation, parameter provenance) are independently verified before it ships, and its explanations are machine-checked against the math.

Nothing about any user is known at build time. Ages, filing status, state, accounts, income, goals and assumptions are collected at runtime by a first-run setup flow and live only in one local encrypted plan file. **Design intent for that flow: a baseline in about ten minutes.** It is an aspiration that shapes the field list, not an exit criterion — what the suite asserts is the field count and the resulting outputs (section 7, item 6).

**Requirement capabilities (a)-(i).** The milestone criteria, the cut rule (section 4.12) and the definition of done (section 7) cite the product's capabilities by these letters; this list is their only definition.

- **(a) Exact federal tax and the household ledger.** The year-parameterised federal return as named lines, payroll, the true marginal rate, the state plug-in at declared fidelity, and the year-by-year cash-flow ledger to the end of the plan (M0-M1, M3; exact state reference modules at M10).
- **(b) The next-dollar question.** One after-tax, risk-matched return per option across 401(k)/403(b), Roth vs Traditional, IRA, backdoor and mega-backdoor Roth, HSA, 529, taxable investing and debt prepayment, with the machine-checked explanation and flip values (M2; the 529 option lands at M10).
- **(c) Roth vs Traditional.** The verdict computed from the household's own projected future marginal rate, with its flip value (the card at M2, the verdict at M3).
- **(d) Scenarios, the first-death machine, the debt planner and import.** Alternatives as diffs over an immutable fact base, the full survivor branch, avalanche/snowball/refinance/prepay-vs-invest, and reviewed snapshot import (M4).
- **(e) Social Security.** Earnings record to PIA, spousal and three-branch survivor benefits, the earnings test and the claiming comparison (entered estimate at M3, computed at M5, the monthly grid at M8).
- **(f) Uncertainty.** Pluggable return generators — deterministic mean path, named stresses, lognormal iid, circular block bootstrap, historical replay as window counts, AR(1) inflation; a regime model and a Student-t stress are deferred to after 1.0 — with Monte Carlo on common random numbers, bit-identical across architectures (M6).
- **(g) Review loop and portfolio allocation.** The annual review attributing every change to facts, assumptions, law or engine; target allocation as `min(tolerance, capacity)`; rebalancing policy as data; asset location; the tax-aware trade list (M9).
- **(h) "Enough" and decumulation.** The scorecard (funded-ratio strip, fail-safe rate, success probability always paired with its magnitude, dollar guardrails), spending rules, Roth-conversion planning, withdrawal sequencing and ACA modelling (M7-M8).
- **(i) Life modules.** Survivor modelling, ACA premium-tax-credit and Medicare/IRMAA in the ledger ship in v1; housing (`Property`), the per-person-year healthcare coverage state machine and the disability/insurance grid are 1.1 by decision (M10, section 5).

### 1.2 Non-goals (v1 and standing)

- Budgeting, a transaction ledger, categorisation, a net-worth-history product. Current state is a **snapshot input** (manual entry, CSV/OFX/QIF import).
- Account aggregation in v1. Institution connections are a committed later phase behind the `Connector` interface.
- A native GUI, Electron/Tauri window, WebView shell, mobile app, hosted or multi-user mode, cloud sync (the ciphertext is portable; syncing it is the user's own choice).
- Windows/Linux packaging, signing or key-store support. Code stays portable behind traits and `cfg`; zero v1 scope is spent there.
- A second engine language, a browser-side engine, dynamic plug-in loading or scripting, any in-process GPL/AGPL/PolyForm/Parity code.
- Exact income-tax modules for every state in v1 (the plug-in interface, no-income-tax states, a user-entered effective-rate fallback and two reference exact modules ship; the rest are incremental).
- Optimizer-generated target allocations, automated tax-loss harvesting, product or fund selection, trade execution, a scored risk questionnaire.
- An in-house LP/MILP optimizer, regime-switching fits, Sobol sampling, stochastic long-term care, HECM principal-limit tables, estate and trust modelling beyond a heirs-rate haircut, WEP/GPO (repealed).
- Telemetry, crash upload, silent auto-update, runtime LLM-generated advice or explanations.
- A lone probability-of-success gauge, anywhere, ever.
- The application is an educational modelling tool, not advice; it prints its assumptions beside every recommendation.

## 2. Guiding principles

1. **Correct before broad.** No feature merges without its fixtures. Tier 1 (statute and IRS worked examples with line-level intermediates) gates hard; nothing is "approximately right" in the tax, Social Security or money layers.
2. **Every milestone produces a number a user can read, explain and export.** No infrastructure-only releases. Stopping after any milestone leaves a coherent tool.
3. **Be slow about eight seams, fast about everything else** (section 3). The seams are frozen early even when what sits behind them is a stub; everything else may be naive and is deepened in place.
4. **Auditability is a data structure.** The `Line` trace node and the typed `Explanation` tree are engine outputs with a reconciliation invariant under property test. The UI renders them; it never composes financial reasoning.
5. **One engine, pure and deterministic.** Rust crates with no I/O, clock, entropy or global state; enforced by compiling them to `wasm32-unknown-unknown` in CI. The front end never computes money and never applies patches.
6. **Assumptions are first-class public data.** Every parameter is sourced, dated, carries a projection rule and a rounding rule, belongs to an immutable vintage and is overridable in a separate visible layer. Every stored result is pinned.
7. **The hard privacy rules are mechanical, not procedural.** One encrypted plan file; TLS on loopback only; nothing persisted in the browser; zero outbound connections by default; the repository mechanically rejects user data. Each is enforced by a test, a lint or a build constraint.
8. **Never claim more than the ledger can support.** A recommendation that depends on inputs the engine does not yet model is withheld or presented as a sensitivity statement (a flip value), never as a computed verdict. Every result prints its validation basis (`tier-1 exact`, `oracle-checked`, `single-oracle`, `property-tested only`) and every state result prints its fidelity.
9. **The copyleft boundary is architectural.** GPL/AGPL tools are reached only through a subprocess and a file format, at test time, and their outputs are recorded so everyday CI installs no copyleft package.
10. **AI assistance is controlled by ground truth it cannot edit.** Fixtures are written from the primary source before the implementation is requested; the assistant never authors both a constant and the test that checks it; CI path rules protect tier-1 fixtures and released vintages; dollar literals are banned from engine crates; development sessions use synthetic data only.

## 4. Milestone roadmap

Eleven feature milestones plus a **recurring parameter-vintage milestone (MV)** scheduled in each autumn publication window, **71 weeks nominal** for a solo developer with AI assistance, published as a planning **range of 71-85 weeks** (the nominal figure widened by the same 20% band that arms the checkpoints in section 4.12, so the range and the trigger describe one thing).

**How these figures are built.** Each milestone is estimated as three separately counted classes of work — **engine**, **UI**, and **release and fixtures** — and the total is their sum. A single optimism multiplier applied to the whole milestone is not used, because it was derived from engine-shaped estimates, makes the front end invisible in every milestone, and is unfalsifiable: every challenge is answered with "the correction is already in". Anything that cannot be split into those three classes is not estimated here. The **per-milestone release tax** — notarization with manual approval, the double build, a new persona journey, the regenerated validation report and the threat-model delta — is the floor of the third column and is never zero.

### 4.1 M0. Trust rails, release spine and the first number (7 weeks: engine 2.0, UI 1.5, release and fixtures 3.5; walking-skeleton checkpoint at week 2)

**Goal.** Prove the whole distribution, transport and correctness chain with a trivial but real calculation, before any user data exists.

**Prerequisite (before week 1).** Apple Developer Program enrolment, and **open decision 2 closed** (enrolment plus custody of the signing credentials and the Ed25519 release key). Recent macOS removed the Control-click bypass for un-notarized software, so the programme is a hard dependency with an enrolment delay.

**Intra-M0 ordering, so enrolment cannot stall the milestone.** M0 has two checkpoints and only the second needs signing.

1. **Walking skeleton, week 2 — explicitly requires no signing:** workspace, CI, `pfp-money`, `pfp-params`, TLS bootstrap and the canonical origin, the app shell, the rate-schedule number. Everything in this checkpoint is verifiable on an unsigned local build.
2. **Signing block, later in M0:** Developer ID signing, hardened runtime, notarization, the stapling experiment, DMG and tarball channels, `spctl` / `stapler validate`, the clean-account offline first launch, and gate items 4 and 5.

**Decision point at week 3:** if enrolment is still incomplete, M1 begins on M0's engine deliverables and the **M0 tag waits**. No milestone after M0 may be tagged until the signing block lands and M0 is tagged, so the debt is visible and bounded rather than deferred silently.

**Scope IN.**
- Cargo workspace, `rust-toolchain.toml`, lockfiles, `xtask`. CI: fmt, clippy, tests, `cargo-deny` (advisories, licence allowlist, bans, sources), `cargo-audit`, `npm ci --ignore-scripts`, `npm audit signatures`, per-package `license-checker`, gitleaks (pre-commit via lefthook, CI, nightly full-history) with custom rules (plan-file magic bytes, SimpleFIN access-URL pattern, FRED-style keys, Apple `.p8`/`.p12`), data-hygiene linter, CODEOWNERS-style protected-path check for `fixtures/tier1/` and locked `params/` vintages, dollar-literal lint for engine crates, `wasm32-unknown-unknown` purity build.
- `pfp-money` (S2) with property tests; `pfp-params` (S1) with the first vintage: 2025 and 2026 ordinary brackets and standard deductions for all filing statuses, **the statutory base-year amounts (`base_year`, `base_values`) per filing status and the archived index series each table's projection rule reads**, provenance with archived checksummed sources; `pfp-explain` with the `Line` node; a rate-schedule function `schedule_tax(year, status, taxable_income) -> Lines`. The base-year amounts and base years are **hand-verified against the statute before this vintage locks** (R11): the standard deduction runs from its 2024 post-OBBBA base, and each bracket table's base year is confirmed against 26 USC 1(f) rather than inferred.
- `pfp-server` + `pfp-app`: loopback-only bind, TLS-only listener (no plaintext acceptor compiled into release), name-constrained local CA with discarded key, trusted leaf, canonical origin `https://127.0.0.1:<port>`, launch token in the URL fragment, `__Host-` cookie plus `sessionStorage` proof token, Host/Origin/`Sec-Fetch-Site` guards, exact security headers, single-instance lock, `RLIMIT_CORE=0`, `Redacted<T>`.
- Embedded Vite + React + TypeScript shell; OpenAPI generated from Rust DTOs and snapshot-tested; Observable Plot under the strict CSP (spike with documented fallback). **Accessible form and table patterns established here, on one screen, where they are nearly free:** labelled controls, deliberate focus order, live regions for streaming progress, and non-colour encoding for every chart series.

- **Keychain/entitlement spike** (`SECURITY.md` §4, before the release form is frozen): confirm that a login-keychain item with the required accessibility intent, an ACL bound to `identifier` + leaf `subject.OU`, and an **empty entitlements set** is creatable and readable in both release channels. If the guarantee turns out to need the data-protection keychain, the entitlement question becomes an ADR, not an implementation detail.

- `cargo xtask validation-report` producing the report from whatever corpora exist, plus the About page route that embeds it. Sections that do not exist yet render as "not yet introduced (milestone Mx)" rather than being omitted, so the report is honest at M0 and complete later.
- `docs/threat-model.md` (T1-T7 table, out-of-scope statement), `docs/data-classification.md`, `docs/contributing.md` (the synthetic-data-only rule, the AI-assistance protocol of ADR-022, the redacted diagnostics-bundle procedure), `docs/licence-watchlist.md` (the restrictions that `cargo-deny` and `license-checker` pass silently, each row date-stamped with the day it was checked: TPAW's PolyForm Noncommercial reported as `NOASSERTION`, AnyPIA-js's absent licence, AnyPIA's own **no-stated-licence** page where US-government public domain is a presumption, the unlicensed reference repositories, the dormancy dates of pinned tier-2 suites, and any third-party capital-market-assumption set whose redistribution terms are unconfirmed), and `docs/assumption-catalogue` generated from `params/` (authoritative for parameter ids). These are controls, not documentation: the contributor rules are the control for the project's dominant development risk (R15) and development is AI-assisted from day one.

The magic-byte commit hook and the user-data pattern check take **no allowlist, ever** — an exception for one path would permanently blind the single control that catches a real household file committed by accident. Consequently the demo plan ships as the plaintext JSON fixture named in section 4's preamble, and `tools/pfplan-ref/` test data is generated at test time, never committed.
- CSV/JSON export helper with spreadsheet formula-injection escaping.

**Scope OUT.** Any user data, the plan file, the federal return beyond the rate schedule.

**Acceptance.**
- Uprating reproduces every published 2026 bracket threshold and standard deduction **from the statutory base-year amounts and the archived index series**, with `basis: IncreaseOverBase` applied **once** to the increase over the base year (26 USC 1(f)(7): $50 down; $25 for the MFS table; the standard deduction from its 2024 post-OBBBA base). The prior year's published value is never the input to the projection, because chaining year over year rounds twice and reproduces most but not all published thresholds.
- **Negative test:** a year-over-year chain, computed from the 2025 published values, is asserted to **diverge** from the statutory result on at least one 2026 threshold. A fixture that passes under both computations is not a test of this rule.
- Derived 2026 MFJ grid to the dollar: taxable 100,000 -> 11,504; 150,000 -> 22,424; 250,000 -> 45,196, with `Line` intermediates.
- On a clean macOS account the DMG opens with only the standard notarized-download dialog; `spctl -a -vv` reports Notarized Developer ID; `stapler validate` passes; first launch succeeds **with networking disabled**. The stapling experiment's result is recorded in `DECISIONS.md` ADR-003.
- Safari, Chrome and Firefox load the canonical origin without a warning after one trust authorisation; declining still works with a fingerprint-compare path. The check runs **headlessly under CI's non-interactive trust provisioning**, and the release notes name every browser that runs per PR, every browser that runs only at release, and any step that remains manual.
- Foreign `Host` -> 421; foreign `Origin` -> 403; on `/api/**` a missing or non-`same-origin` `Sec-Fetch-Site` -> 403, while a top-level navigation to `/` carrying `Sec-Fetch-Site: none` with `Sec-Fetch-Mode: navigate` **is served** (the route-scoped rule of `SECURITY.md` §7.2, [S-01]); plaintext HTTP connection fails; listener is loopback only; headers exact-match snapshot; CSP violation count zero; `localStorage`, IndexedDB and Cache Storage empty and `sessionStorage` holds only the proof token; no third-party requests; cold start to browser under two seconds.
- Two independent CI builds are compared and the unsigned SHA-256 and the `xtask` difference report are **published**. At M0 and M1 this criterion is *reported*, not gating (R21); it gates from M2, by which point the front-end determinism work has had two milestones to converge.
- No `.pfplan` container-magic byte sequence exists anywhere in the tree or in the release archive; the check has no allowlist. SBOM contains no copyleft component; the server passes an integration test under a deny-outbound sandbox profile.
- `axe` reports no serious or critical violation on the shell, the Assumptions Registry and the rate-schedule screen.

**Dependencies.** Apple Developer Program (signing block only; see the intra-M0 ordering above).

**What a user can do now.** Download, launch, see a trusted local page; browse the Assumptions Registry (every parameter with source, as-of date, vintage, projection and rounding rule); enter filing status, year and taxable income and get the rate-schedule tax with every line explained and exportable; see how thresholds are projected forward under an editable inflation assumption.

### 4.2 M1. Exact federal return for one year, and the encrypted plan file (9 weeks: engine 5.0, UI 1.5, release and fixtures 2.5)

**Goal.** `federal(year, status, inputs, params, trace) -> named lines`, exact for current law on its covered inputs, exposed as the **Tax Year Explorer**; and the vault, so that what the user types is encrypted from the first keystroke that is saved.

**Scope IN.**
- `pfp-tax` (S3): ordinary brackets; LTCG/QDI stacking; Pub 915 taxable-Social-Security worksheet; standard deduction with aged/blind add-ons; senior deduction (2025-2028) with phase-out; itemizing test (SALT cap as a dated schedule with phase-down, $750k acquisition-debt cap, charitable floor); child and other-dependent credits; NIIT; Additional Medicare; payroll function (OASDI wage base, Medicare, SE tax on 92.35%); RMD start ages and Uniform Lifetime / Joint divisors; `marginal(base, delta)` running the function twice; point and block EMR for ordinary income and LTCG. Rate-schedule formula is canonical; IRS Tax Table mode lives only in the validation adapter.
- **The whole S3 signature, including its performance escape hatch and its cost context, frozen here** rather than reopened at M6: `trace: TraceLevel` on `federal()`, `payroll()` and `marginal()`, where `None` returns totals and typed accessors with `lines` empty; and `CostCtx` with `MarginalRate::components` frozen at its four members — `federal`, `state`, `irmaa_pv`, `ptc_lost` — which sum to `block x delta`, plus `memo: {niit, addl_medicare}`, two lines that are **already inside `federal`** (`f8960.*` and `f8959.*`, `ENGINE-SPEC.md` §3.2) and are shown for the reader, never summed again: counting NIIT or Additional Medicare as a fifth component would double them in every EMR and every `r_u`. `state` is supplied by a `StateTax` trait object defaulting to `NoIncomeTax`; `irmaa_pv` and `ptc_lost` are structurally present, zero, and each raises a `NotModelled` entry until M3 and M8 respectively. `marginal()` underlies the Roth decision, the EMR curve and every `r_u`, so its shape cannot change later without breaking "later worksheets are additions, never signature changes".

Nothing bounds a full `project()` path-year before it exists.

### MV. Parameter vintage (2 weeks, recurring; scheduled in each autumn publication window; unnumbered because it recurs between milestones)

**Why it is a milestone and not an assumption.** A 71-week schedule beginning in September 2026 crosses **two** annual tax-parameter publication cycles: the autumn 2026 window (IRS Rev. Proc. and Notice, the SSA Federal Register notice, the CMS fact sheet, HHS/ASPE guidelines) straddles M0 and M1, and the autumn 2027 window falls around M7 and M8. **MV's two weeks float to the documents, not to the week number in the roadmap table:** each document appears when it appears, the last of them (typically the CMS fact sheet) sets the start, and the weeks land in the nearest gap between milestones rather than at a committed week. Detection is already handled — dated parameters with scenario toggles, vendored CC0 values, recorded oracle outputs and the nightly re-record as the early warning (R10) — but detection is not a work budget. Budgeting zero weeks for the work the whole engine's currency depends on is how the current-year vintage becomes the thing that slips under pressure.

**Scope IN.** The thirteen-step annual-update procedure in `TESTING.md` §12, whose steps *are* the acceptance criteria: archive each primary document with `sha256` and publisher URL; **hand-verify every changed value against the archived text**; open a new vintage directory (never edit a locked one); declare projection and rounding per table, with never-indexed items carrying `flat` explicitly; constants-sync test against the archived text; uprating reproduction from the statutory base-year amounts under `basis: IncreaseOverBase`; per-table delta report reviewed in the PR; lock `VINTAGES.lock`; **re-record the oracles** and triage the tier-3 diff; golden review with an `engineVersion` bump; clear whatever hand-verification-gate items that year's documents resolve and carry the rest forward with the reason; regenerate the validation report and the Assumptions Registry; and test that a result pinned to the old vintage shows as stale and re-runs only on request with the difference shown.

**Scope OUT.** Any feature work. MV is a milestone so that its weeks are visible, not so that it becomes a place to hide them.

**Dependencies.** The publication of that autumn's primary documents — a calendar dependency, not a code one. **Note:** hand verification is serial and is the one part of this milestone AI assistance cannot compress (R22); the assistant may transcribe, a human confirms, and the assistant never authors both a constant and the test that checks it.

### 4.4 M3. Lifetime ledger and the Roth-vs-Traditional verdict (7 weeks: engine 5.0, UI 1.5, release and fixtures 0.5)

The build is spiked at M1. **If AnyPIA cannot be stood up**, `pfp-ss`'s validation basis is `oracle-checked` on the Open Social Security and ssa.tools tier-2 suites plus the tier-1 `ss_claim_factor_knife_edge` gate, **printed on every PIA result**, and the milestone still ships; the tier-1 exact claim is withdrawn rather than asserted on a fixture set that does not exist.

**Dependencies.** M3 (M4 for survivor streams). **What a user can do now.** Replace the entered estimate with a benefit computed from the earnings record and see how stopping work early, or a trust-fund shortfall, changes the plan and the Roth answer.

### 4.7 M6. Uncertainty: pluggable generators and Monte Carlo (5 weeks: engine 3.5, UI 1.0, release and fixtures 0.5)

**Scope IN.** `pfp-sim`: lognormal iid with **arithmetic-mean inputs** and Cholesky correlation (one draw per asset class per period; accounts mapped to allocations); circular block bootstrap of joint rows; named stresses (bad timing, bear-market replay, cohort presets); historical replay reported as integer window counts; AR(1) inflation (mean editable; default preset `quantcalc` with phi 0.4495, sigma 0.80% — a published third-party fit, `SIMULATION-SPEC.md` §5 — and the unfitted heuristic phi 0.65, sigma 1.75% shipped only as the labelled `high-persistence-stress` preset; a committed refit on CPI from 1913 is a **blocking gate for the M6 vintage lock**, `SIMULATION-SPEC.md` §5); ChaCha8 with stream = path index; in-repo Wichura AS241 inverse CDF with golden vectors; pure-Rust `libm`; `simulate(&[ResolvedPlan])` sharing one shock tensor; run-size contract (ephemeral 1,000; saved 5,000; solvers and tails 10,000+); Wilson interval beside every rate; fan chart with the deterministic overlay; the next-dollar distributional check (5th/50th/95th net worth for the recommendation vs its alternative); assumptions sheet per run; NDJSON progress over `fetch`. **Accessibility of the new surfaces is scope, not cleanup:** an accessible fan chart and streaming-progress region (live region, no colour-only encoding), and every chart's data available as a table.

**Scope OUT.** Regime-switching, Student-t stress, Sobol; bundling historical datasets or third-party capital-market-assumption sets whose redistribution terms are unconfirmed (a loader, the documented file shape, published checksums and the user's own entry ship instead; `SIMULATION-SPEC.md` §3.2, §4.4).

**Acceptance.** Moment match to 1e-9 (m 7%, s 15% -> sigma^2 0.019462, mu 0.057928, geometric 5.9638%); same seed **bit-identical on aarch64 and x86_64 and independent of thread count**; KS test against target; CRN A/B variance lower than independent streams; zero-volatility generator equals the deterministic run; Bengen longevity smoke test on a declared data series; performance gates (1,000 x 60 under 250 ms; 10,000 x 60 under 2 s on Apple Silicon).

**Dependencies.** M3. **What a user can do now.** See outcome ranges for any scenario, stress the plan against named bad histories, and get a statistically meaningful comparison of two allocations on identical random paths.

### 4.8 M7. The "enough" scorecard and decumulation spending rules (4 weeks: engine 3.0, UI 0.75, release and fixtures 0.25)

**Scope IN.** Funded ratio (essential at a TIPS-like rate, total; home equity excluded) as a sensitivity strip, never pass/fail; horizon-appropriate historical fail-safe rate; success probability **always paired** with `max_cut`, worst-decile cut and shortfall timing; dollar guardrails (the published product-default preset plus two named alternatives); spending rules (constant real, Vanguard dynamic, Guyton-Klinger, amortization/VPW, ratchet, CAPE rule, risk-based guardrails); sustainable-spending bisection (default solver target 85%, adjustable 50-95%); spending at 95/90/80/70/50% with the unspent-legacy distribution; stochastic mortality with P(both), P(only A), P(only B); selectable, printed success criterion.

**Acceptance.** Vanguard dynamic path 40,000 -> 42,000 -> 41,543; Guyton-Klinger assertions transliterated from cFIREsim-open (Apache-2.0); Milevsky-Robinson ruin 7.14 / 13.87 / 22.07 / 31.01% within +/-0.02; **API-level test that a probability cannot be serialized without its magnitude fields**, plus a component test; folklore targets ("4.15%", "$74,146") refused in fixture notes.

**Dependencies.** M6. **What a user can do now.** Answer "is it enough, and what would a bad decade cost in dollars?" on one scorecard.

### 4.9 M8. Roth conversions, withdrawal sequencing, claiming grid, ACA (5 weeks: engine 4.0, UI 0.5, release and fixtures 0.5)

**Scope IN.** Fill-to-threshold primitive (bracket top, LTCG boundary, IRMAA tier, FPL multiple); tax-equilibrium loop (future rate = median EMR over late-life years using single-filer tables after the assumed first death; 3-5 iterations); five-year clocks; after-tax terminal wealth with an editable heirs rate; bracket-managed and proportional withdrawal policies; ACA PTC estimate-and-reconcile with the 400% FPL cliff as a dated, switchable parameter and the two MAGI definitions on two clocks; monthly 62-70 claiming grid with top candidates re-ranked through the ledger.

**Scope OUT.** In-house LP/MILP optimizer; inherited-IRA schedules beyond spousal cases.

**Acceptance.** BETR closed form reproduces 35 / 30.1 / 23.5 / 14.1%; Form 8962 examples; Owl example cases as out-of-process recorded **bounds**, not targets; Open Social Security PV fixtures with the mortality table checked into fixtures.

**Dependencies.** M5, M6. **What a user can do now.** Get a year-by-year conversion plan with the EMR curve as its explanation, a withdrawal order, and a claiming strategy, each compared on lifetime taxes and after-tax terminal wealth.

### 4.10 M9. Review loop, portfolio allocation and tax-aware reallocation (5 weeks: engine 3.0, UI 1.5, release and fixtures 0.5)

**Scope IN.** Annual Review wizard and quarterly light refresh; snapshot diff answering **"why did the plan change?"** by attributing each KPI delta to facts vs assumptions vs law (parameter vintage) vs engine version; parameter-vintage update flow with per-table deltas before acceptance; Full Plan and Review reports as print routes. Target allocation as `min(tolerance, capacity)` with need solved (tolerance entered as a maximum equity share against a dollar loss scenario); glide paths as pure functions; rebalancing policy as data (5/25 bands); asset location by tax drag; least-tax-first lot selection under a gains budget; household-wide wash-sale hard block across both people's accounts; four plans side by side (full, to band edge, cash-flow only, do nothing); positions and lots import.

**Acceptance.** Replaying a synthetic two-year persona history yields a review record attributing KPI deltas to each cause; re-rendering an old snapshot under a newer binary reproduces identical numbers **or reports the pin mismatch and shows the difference** (no bit-reproduction claim); dollars conserved across every rebalance; no generated trade list violates the 61-day window (property test).

**Dependencies.** M4, M7. **What a user can do now.** Run an annual review and see exactly what changed and why; choose a target allocation with reasons and receive an explained, tax-aware trade list.

### 4.12 Cut rule and schedule checkpoints

**Trigger, restated as a ratio applied at every checkpoint** rather than once at M6 exit. At each checkpoint, compare cumulative *actual* elapsed weeks against cumulative *nominal* weeks:

| Checkpoint | Nominal week | Response at >20% cumulative overrun |
|---|---|---|
| M2 exit | 27 | **Re-baseline every remaining milestone by the observed ratio** and publish the new range; apply cut tier 1 immediately |
| M4 exit | 41 | Re-baseline; apply cut tiers 1-2 |
| M6 exit | 51 | Re-baseline; apply cut tiers 1-3 |
| M8 exit | 62 | Re-baseline; apply cut tiers 1-5 |

M6 exit alone was too late to matter: slip accrued in M0-M2 stayed unobservable for nine months, and the relief available at that point was smaller than the overrun that triggered it, so the rule was guaranteed to under-deliver at exactly its own threshold.

**Ranked cut list.** Each tier carries the sentence that goes in the release notes.

1. **OFX/QIF importers -> 1.1**, keeping CSV. *"Version 1.0 imports balance and holdings snapshots from CSV; OFX and QIF import follow in 1.1."*
2. **The remaining progressive setup sections at M4 -> 1.1.** Quick Start plus the fields the ledger and waterfall consume stay. *"Version 1.0 collects the fields the projection reads; the remaining optional detail sections follow in 1.1."*
3. **The monthly 62-70 claiming grid (M8) -> 1.1.** The 62 / FRA / 70 comparison through the ledger stays. *"Version 1.0 compares claiming at 62, full retirement age and 70; the month-by-month grid follows in 1.1."*
4. **M9's trade-list generator -> 1.1.** The review loop, the target-allocation choice and the rebalancing policy stay. *"Version 1.0 recommends a target allocation and shows the gap; the tax-aware trade list follows in 1.1."*
5. **M10's second exact-state reference module -> 1.1.** The `DeclarativeState` interpreter and one module stay. *"Version 1.0 ships one exact state module and the data format for contributing others."*

**Never cut:** fixtures, the security suite, the release gate, result pinning, the explanation invariant, **the current-year parameter vintage** (the MV milestone is what makes every number on screen current, and it is therefore the thing that must not become the slack), and **the 529 option of capability (b)** (section 1.1), so a cut cannot silently drop a named capability.

### 4.13 Release gate (every milestone)

Items are **scoped by the milestone that introduces the thing they check**, so that M0 does not ship failing its own gate and set the precedent for waiving it later.

1. CI green: all three fixture tiers, properties, fuzz budget for touched parsers, `wasm32` purity build. **From M1:** the surviving-mutant budget for touched money/tax/SS crates (`cargo-mutants` is introduced at M1 and its initial budget integers are set at M1 exit).
2. Security integration suite green (vault, server, browser, parsers, supply chain, release rows of the security test matrix).
3. Reproducible double-build: unsigned SHA-256 compared across two runners, digest and difference report published. **Reported at M0-M1; gating from M2** (R21).
4. `codesign --verify --strict`, `spctl`, `stapler validate` pass; hardened runtime, no entitlements.
5. CycloneDX SBOM and provenance attached; SBOM asserts no GPL/AGPL/PolyForm/Parity component; `cargo-deny` and `npm audit signatures` clean; per-package front-end licence check clean.
6. Threat-model delta reviewed in the release PR.
7. Any golden-snapshot change is accompanied by an `engineVersion` bump and a reviewed diff.
8. Validation report regenerated by `cargo xtask validation-report` and embedded in the About page. **From M0**, with whatever corpora exist and sections that do not exist yet rendered as "not yet introduced (milestone Mx)"; **oracle versions and mutation score from M1**.
9. Persona Playwright journeys pass against the signed artifact.
10. `axe` clean at **serious and critical** across every persona journey screen. The UI is dense forms, data tables with per-cell explain panels, SVG charts and print routes: established at M0 on one screen this is nearly free, discovered at M6 across six journeys it is not.
11. **Licence watchlist reviewed and signed off by a human in the release PR** (`docs/licence-watchlist.md`), **and `NOTICE` checked complete** against the enumerated list of ported and transliterated sources in ADR-004: every permissive source the release ports or transliterates has a `NOTICE` entry with repository URL, licence and pinned commit, and every status claim in the watchlist carries the date it was last checked. This is the one non-mechanical licence control — `cargo-deny` and `license-checker` pass TPAW's `NOASSERTION` and AnyPIA-js's absent licence silently — and without a gate item it has nowhere to run.

## 7. Definition of done for v1.0

1. **Capabilities.** Capabilities (a) through (h) of section 1.1 accepted per the milestone criteria above, with the 529 option inside (b) landing at M10 and (g) delivered by M9. Capability **(i) ships in part**: the survivor module (M3 estimate, M4 full first-death machine), ACA premium-tax-credit modelling (M8) and Medicare/IRMAA in the ledger (M3). **Housing (`Property`), the per-person-year healthcare coverage state machine and the disability/insurance grid are 1.1 capabilities by decision**, stated as such in the release notes, with their schema shapes reserved in seam S5 so 1.1 is additive. Nothing here rests on a contingency firing: a definition of done whose satisfaction depends on the cut rule is not a definition of done.
2. **Distribution.** One universal executable; stapled DMG channel and bare-binary tarball channel from the same byte-identical Mach-O; Developer ID signed, notarized, hardened runtime without entitlements; first launch succeeds offline on a clean account; reproducible unsigned digest published; SBOM with the no-copyleft assertion; no runtime to install.
3. **Privacy and security.** All user data in one encrypted plan file; passphrase slot always present; Keychain slot opt-in, non-synchronizable, asserted by test; TLS-only loopback listener; nothing in browser storage beyond the proof token; zero outbound connections by default, verified under a deny-outbound sandbox; security suite green; gitleaks and the data-hygiene linter in pre-commit and CI; external review findings at zero high; published format spec, threat model and reference decryptor.
4. **Trust.** Tier 1 at 100% with no tolerance; Tier 2 suites pinned with skip counts reported; Tier 3 goldens reviewed; conservation residual exactly zero on every persona and every property case; mutation budget met on money, tax and SS crates; cross-architecture bit-identity test green; validation report embedded in the About page.
5. **Transparency.** Every parameter and assumption visible with source, as-of date, vintage, projection and rounding rule, and override state; every stored result pinned to engine version, schema version, parameter vintages, assumption set, seed, generator configuration, inputs hash and binary digest; stale results marked, re-run on request with the difference shown.
6. **Product.** Quick Start reaches a baseline in **at most the sixteen fields of `DOMAIN-MODEL.md` §18.1** and produces the current-year ledger row, the tax picture, the KPI strip and the next-dollar waterfall, asserted by each persona journey. (The design intent of "about ten minutes" lives in section 1; it is not restated here, because the only mechanised check deliberately measures the field count and the resulting KPI set rather than a wall clock that is undefined as to user, hardware and typing speed.) Every recommendation carries Why / What would change this / Adopt; the One-Page Plan and review report print from pinned view-models; **`axe` reports no serious or critical violation on any persona journey screen**; no screen, export or API response carries a success probability without its magnitude companions.
7. **Repository.** Contains only code, docs, public parameter tables with provenance and clearly labelled synthetic fixtures; all documentation is user-agnostic.
