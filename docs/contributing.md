# Contributing

This is a financial-planning application whose correctness claims are only as good as the
controls around them. Two of those controls are procedural rather than mechanical — what may
be committed, and how AI assistance is used — so they are written down here and enforced by
the gates listed in [Commit hygiene](#7-commit-hygiene-hooks-and-gates).

The design documents in [`docs/`](.) are the specification. This page does not restate them;
it collects the rules a contributor has to follow before a first commit, and cites the section
that owns each one. Where this page and a design document disagree, the design document wins.

Start with [`PLAN.md`](PLAN.md) §4 for the milestone you are working in,
[`ARCHITECTURE.md`](ARCHITECTURE.md) §3 (repository layout) and §4.3 (the purity and
determinism rules), [`SECURITY.md`](SECURITY.md) §13 (repository hygiene) and
[`TESTING.md`](TESTING.md) §11 (CI stages and merge gates).

Build and test commands are in the repository [`README.md`](../README.md), under
"Development".

## 1. The repository is the application only

No user's information, profile, selections or results are ever committed
([ADR-023](DECISIONS.md)). The repository holds code, documentation, public parameter tables
with provenance, and clearly labelled **synthetic** fixtures. Nothing else.

### 1.1 What may be committed

| May be committed | Never committed |
|---|---|
| Source, tests, tooling, documentation | Any real person's figures, balances, holdings or transactions |
| Parameter tables under `params/`, each with a primary source, an as-of date, an archived checksum, a projection rule and a `RoundingRule` | Any encrypted plan container (see §2), any export, any `.env` file |
| Fixtures under `fixtures/`, each either marked synthetic or carrying a published-source citation | Signing material or private keys of any kind (`.p8`, `.p12`, `.cer`, `.pem`, `.key`) |
| Archived primary text under `params/provenance/`, with checksums | Institution credentials, API keys, access URLs, tokens |

`local/` is git-ignored developer scratch. It is never published, and there is no exception
to that. Upstream corpora that cannot be redistributed are fetched into git-ignored caches —
PolicyEngine-US YAML into `.policyengine-cache/`, never into the tree ([`SECURITY.md`](SECURITY.md)
§13.1, §13.3).

### 1.2 Where data files may live

The data-hygiene linter (`cargo xtask data-hygiene`, `SECURITY.md` §13.3) enforces this:

- Any `.json`, `.csv`, `.ofx`, `.qif`, `.yaml`, `.yml` or data `.toml` file under version
  control must live under `fixtures/` or `params/`. Tool configuration in those formats
  (`Cargo.toml`, `package.json`, workflow YAML, editor and CI settings) is configuration, not
  data, and is recognised as such.
- A data file anywhere else fails the gate. If you need scratch data while working, put it in
  `local/`.

### 1.3 How fixtures are marked synthetic

Every file under `fixtures/` carries **one** of two things (`SECURITY.md` §13.3(2)).

Either the synthetic marker, with the generator that produced it and its seed:

```json
"synthetic": true,
"generator": "xtask persona --kind two-earner-couple",
"seed": 424242
```

Or a citation block, when the fixture is a published worked example:

```json
"citation": {
  "title": "...", "publisher": "...", "url": "https://...",
  "page": "...", "retrieved": "YYYY-MM-DD", "sha256": "..."
}
```

A fixture with neither fails the gate. Persona fixtures are **generated by the seeded `xtask`
generator**, never hand-written, so that they are obviously synthetic and regenerable
(`SECURITY.md` §13.3(5)).

Parameter tables under `params/` carry provenance instead:

```toml
[[source]]
title = "..."
url = "https://..."
retrieved = "YYYY-MM-DD"
sha256 = "..."
```

plus an as-of date, a projection rule and a rounding rule. A table without a projection rule
is a CI error, not a warning (`SECURITY.md` §13.3(3), `TESTING.md` §11.2 gate 9).

### 1.4 Locked vintages are immutable

`params/VINTAGES.lock` holds a SHA-256 per file. A changed hash fails CI. **A corrected
parameter value ships as a new vintage, never as an edit to a locked one**
(`SECURITY.md` §13.3(4), `TESTING.md` §11.2 gate 10). Pinned results stay reproducible
because the vintage they were computed under cannot move under them.

### 1.5 Patterns that fail automatically

`SECURITY.md` §13.4 specifies a user-data and credential pattern check of seven rows, run on
every diff and nightly over full history. The scaffold implements the rows that have something
to check today; the rest land with the pull request that creates what they inspect. Each row
below says which.

Live now — these fail at pre-commit and in CI:

- The container magic anywhere in any file — `cargo xtask check-magic`, plus `--history`
  nightly over every blob; see §2.
- An SSN-shaped string (`NNN-NN-NNNN`) in any committable file — `cargo xtask data-hygiene`.
  The documented fixture allowlist exists and is empty.
- A JSON document containing `"schemaVersion"` together with `"accounts"` or `"persons"`
  outside `fixtures/plans/` — `cargo xtask data-hygiene`. A JSON document is a `.json` file or
  any file whose content opens like a JSON object.
- A fixture with neither the synthetic marker nor a source citation — `cargo xtask
  data-hygiene` (§1.3).
- An `asOf`-stamped JSON fact file outside `fixtures/` — `cargo xtask data-hygiene`.

Not implemented yet — specified, and tracked in §8 item 4:

- Real-looking email addresses or street addresses in fixtures. Lands with the M0 step that
  creates `fixtures/`; until then there is no fixture for it to read.
- A passphrase-shaped CLI flag, or an `env::var` passphrase lookup, anywhere in `pfp-app`, in
  **any** build profile. Lands with the pull request that gives `pfp-app` a command line.
- The nightly full-history sweep of the three `data-hygiene` rows above. `data-hygiene` reads
  the working tree (every tracked or committable file, on every commit and pull request), not
  old blobs; only the container magic and gitleaks rules are swept over history today.

Use obviously-synthetic contact details and generic personas — "an early-career single filer
with student debt", "a two-earner couple with a mega-backdoor-capable plan" — never a real
name, address or household.

## 2. The container-magic rule takes no allowlist, ever

An encrypted plan file (`.pfplan`) begins with a fixed byte sequence. If that sequence appears
**anywhere** in any file of the working tree, or anywhere inside a release archive, the build
fails: `cargo xtask check-magic`, a commit hook, and a gitleaks rule all look for it, from M0
onward (`SECURITY.md` §13.2, §13.4; [ADR-023](DECISIONS.md); `PLAN.md` §4.1).

**There is no allowlist and there never will be.** Not for a demo, a fixture directory, a
test, or one path "just this once". This is the single mechanical control standing between a
real household's plan file and a public repository (threat T5), and one allowlisted path
blinds it permanently.

Three consequences a contributor will meet:

1. **The demo plan is plaintext synthetic JSON**, at `fixtures/plans/demo.plan.json`, carrying
   the synthetic marker with its generator and seed. The binary encrypts it into a container
   in the user's own directory at first use. No container is committed, generated into the
   tree, or shipped in a release archive.
2. **`tools/pfplan-ref/` holds no container test data.** Its fixtures are written by the test
   run into a temporary directory and deleted with it.
3. **Detectors are written as escaped or hex patterns.** `xtask/src/magic.rs` spells the
   sequence as hex bytes, and `SECURITY.md` §13.2 describes its gitleaks rules rather than
   reproducing them, so that the detector cannot trip on its own source. This document follows
   the same convention and never spells the sequence literally. Do likewise in any new
   detector, test or document.

If a gate reports the magic in a file you are about to commit, the answer is never to exempt
the path. Remove the file.

## 3. AI-assistance protocol

Development is AI-assisted from day one, and the project's dominant risk (R15) is
plausible-but-wrong financial code with tests that agree with it. [ADR-022](DECISIONS.md)
names three failure modes and pins one control to each (`SECURITY.md` §13.5). These apply to
every contributor, human or assistant; an assistant is simply the case the controls were sized
for.

### 3.1 Self-confirming tests

- **Fixtures are written from the primary source *before* the implementation is requested.**
  The statute, the IRS worked example or the published table comes first; the code that
  satisfies it comes second.
- **The assistant never authors both a constant and the test that checks it.** If an assistant
  produced the expected value, a human reads it back against the primary source before it
  lands — or the fixture is rewritten from the source by hand.
- **A lint bans dollar literals in engine crates outside tests** (`cargo xtask lint-dollars`).
  Statutory amounts come from `params/`, sourced and versioned. There is deliberately no
  per-line escape comment: an amount the engine needs is a parameter.

### 3.2 Hand-verification of parameters

A new parameter vintage is not a transcription exercise. Before a vintage locks, its
**statutory base-year amounts and base years are hand-verified against the statute** (risk
R11, `PLAN.md` §4.1): the standard deduction from its 2024 post-OBBBA base, each bracket
table's base year confirmed against 26 USC 1(f) rather than inferred. Projected values are
computed from the base year and the archived index series, never chained from the prior year's
published value.

Every new table also has to satisfy `TESTING.md` §11.2 gate 9 before it can merge: a primary
source, an as-of date, an archived checksum, a projection rule and a `RoundingRule` — and,
where the rule's basis is `IncreaseOverBase`, a `base_year`, per-breakdown `base_values` and a
named `index_series` that is archived rather than fetched.

### 3.3 Silent ground-truth edits: protected paths

CODEOWNERS-style path checks (`cargo xtask protected-paths`, run pre-commit and in CI) block
edits to:

- `fixtures/tier1/` — statute and IRS worked examples with line-numbered intermediates, the
  hand-worked ledgers and the rounding table. Tier 1 is the hard gate: 100%, no tolerance, no
  skips.
- **Locked `params/` vintages** — see §1.4.

**An AI assistant may not change ground truth to make code pass.** Concretely, these need a
deliberate human decision and review, never an assistant's edit in passing:

| Change | What it requires |
|---|---|
| Anything under `fixtures/tier1/` | Human authorship from the primary source; the protected-path check will otherwise refuse it |
| A locked parameter value | A **new vintage**, with provenance; never an edit in place |
| A tier-3 golden snapshot | An `engineVersion` bump and a reviewed diff ([ADR-010](DECISIONS.md), `TESTING.md` §11.2 gate 4) |
| A test expectation that started failing | Read the primary source first. A failing fixture is evidence about the code until the source says otherwise |
| A hygiene gate's scope, or any allowlist in one | An ADR. The magic-byte gates take no allowlist at all (§2) |

### 3.4 Data exfiltration

- **Development and AI-assisted sessions use the synthetic demo plan only** — never a real
  plan file, never real figures pasted into a prompt, a test, an issue or a commit message.
- **Bug reports use the redacted diagnostics bundle** (§4), not a plan file and not a screenshot
  of one.

### 3.5 Everything user-facing stays user-agnostic

All documentation, fixtures, examples **and commit messages** are user-agnostic: generic
personas and synthetic figures only. No person, household, age, location or personal file path
appears in a tracked file. If an example needs a number, it is a synthetic number and it is
labelled as one.

## 4. Reporting a bug: the redacted diagnostics bundle

The diagnostics bundle (asset **A10**, `SECURITY.md` §8) is the supported way to send state to
someone else. It is a plaintext artifact written deliberately to be read by a stranger, so it
is treated as one:

- **User-initiated only**, preceded by a plain warning and a change-log entry, written to a
  destination the user chooses at mode `0600` — never to a default or hidden path.
- It carries: app version and binary digest, OS and architecture, engine, schema and
  `formatVersion`, parameter vintage ids, feature toggles, collection counts ("4 accounts,
  2 debts"), the last 200 ring-buffer log lines, and the validation report.
- It carries **no** amounts, names, dates of birth, account or institution identifiers, file
  paths, tokens, or import-file content. A CI canary test ([S-25]) generates a bundle from a
  synthetic plan containing a canary value and asserts zero hits.

Attach the bundle to the report. Do not attach a plan file, an export, or a log captured
another way; logs describe control flow, never content (`SECURITY.md` §8), and a screenshot of
a real plan defeats the whole arrangement. If a bug can only be shown with data, reproduce it
on the synthetic demo plan or on a seeded persona fixture, and send that.

## 5. Licence boundary

The project is **Apache-2.0** ([ADR-004](DECISIONS.md)). The boundary below is architectural,
not advisory, and is enforced by `cargo-deny`, a per-package npm licence check and an SBOM
assertion at the release gate.

**Permitted for dependencies:** MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, CC0-1.0,
Unicode-3.0, Zlib. **Anything else needs an ADR** — including a dual-licensed crate whose
scanner output is ambiguous, and anything a scanner reports as `NOASSERTION`. The restrictions scanners pass silently are
tracked, date-stamped, in `docs/licence-watchlist.md` (`PLAN.md` §4.1).

| Class | Example projects | What you may do |
|---|---|---|
| Port with attribution (MIT/Apache/CC0) | Open Social Security, ssa.tools, cFIREsim-open rule tests, Tax-Calculator parameter values | Re-implement in Rust, transliterate tests by `xtask` script, vendor CC0 data into `params/` with provenance. **The `NOTICE` entry lands in the same PR**, with repository URL, licence and pinned commit SHA |
| Out-of-process test oracle only (**GPL/AGPL**) | Owl (GPL-3.0), PolicyEngine-US (AGPL-3.0) | Subprocess plus a file format, **never** linked, vendored, imported or shipped. Adapters are written from scratch. Outputs are *recorded* as goldens so ordinary CI installs nothing copyleft. **Parameter values are never sourced from these projects** — a third-party default may be cited as a comparison, never adopted into `params/` |
| Read-only reference | TPAW Planner (PolyForm Noncommercial), prime-harvesting (Parity), Beancount (GPL-2.0), hledger (GPL-3.0), unlicensed repositories | Read for design; re-derive the equations. No code, no tests, no data copied |
| Not bundled until terms are confirmed | Return datasets and vendor capital-market-assumption sets without explicit redistribution terms | A loader, a documented file shape and published checksums — the user supplies the data |

`oracles/` and `tools/` are **not** Cargo workspace members and are excluded from release
archives (`ARCHITECTURE.md` §10.3). Keep it that way: that exclusion is what makes the
copyleft boundary a build fact rather than a promise.

Third-party names identify published methodologies and imply no affiliation, sponsorship or
endorsement; all trademarks belong to their owners.

## 6. Engine rules worth knowing before the first PR

`ARCHITECTURE.md` §4.3 is the full contract. The four that catch newcomers:

- **No filesystem, network, clock, environment, entropy or global mutable state in engine
  crates.** The plan's `asOf` date and the seed are inputs. The `wasm32-unknown-unknown`
  purity build in CI is what proves it.
- **Money is `Cents(i64)`**; statutory rates are exact `Ratio`; rounding happens **once**,
  through a named `RoundingRule` stored beside the parameter.
- **No new `f64`** in `pfp-tax`, `pfp-ss` or `pfp-money` beyond the two named entry points
  `Cents::grow` and `Cents::from_f64_half_even`. A third is a design change needing an ADR.
- **Determinism**: `BTreeMap`/`IndexMap` rather than hash maps in engine crates; `libm` for
  `exp`/`ln`/`pow`; identical output on both architectures and at any thread count.

Crates are created in the milestone that first needs them. Do not scaffold an empty crate
because the layout in `ARCHITECTURE.md` §3 names it.

**The one exception, and why.** M0 lands as a sequence of pull requests, and its first one is
the scaffold: the workspace, the lint tables, the hygiene gates and CI. That pull request
creates the seven crates M0 itself needs (`pfp-domain`, `pfp-money`, `pfp-params`,
`pfp-explain`, `pfp-tax`, `pfp-server`, `pfp-app`; `PLAN.md` §4.1, `ARCHITECTURE.md` §3) with
a crate-level doc comment and `#![forbid(unsafe_code)]` and no other content, so that the
workspace lints, `clippy.toml`, `deny.toml`, the `wasm32` purity build and
`cargo xtask engine-crates` are wired against real members and proven green before any engine
code exists to hide behind them. Each of those crates receives its first real content in a
later M0 pull request. The exception is exactly that wide: a crate of the *current* milestone,
in that milestone's scaffold pull request. A crate belonging to a later milestone is never
created early, and a skeleton does not outlive its milestone.

## 7. Commit hygiene: hooks and gates

### 7.1 Install the hooks once

```sh
lefthook install
```

The hook set is declared in `lefthook.yml` at the repository root. Do not commit with
`--no-verify`; the pre-commit stage is seconds, and every check in it also runs in CI, so
skipping it only moves the failure later.

### 7.2 Pre-commit (stage 0, `TESTING.md` §11.1)

In `lefthook.yml` order: gitleaks over the staged diff · the container-magic hook (anywhere
in any file of the working tree, ignored files included, **no allowlist**) · the
protected-path check · the data-hygiene linter · the dollar-literal lint · `cargo fmt --check`.

**Clippy runs at pre-push, not pre-commit** — a deliberate departure from the stage-0 list in
`TESTING.md` §11.1, which names "clippy on changed crates". A workspace clippy run after a
dependency change takes minutes; a hook that slow is the hook that gets skipped, and the
pre-commit stage exists for the mistakes that cannot be taken back once committed (a secret, a
plan file, a ground-truth edit). A lint finding can. Pre-push runs
`cargo clippy --workspace --all-targets -- -D warnings` and the test suite, and CI runs both
again.

The `xtask` gates can be run by hand at any time — see the README's "Development" section for
the exact commands.

### 7.3 Per push and per PR (stage 1)

`fmt` · `clippy -D warnings` · `cargo-deny` · `cargo-audit` · workspace build · the tier 1, 2
and 3 verify run (no Python, no network) · property tests at 256 cases · the `wasm32` purity
build · OpenAPI and JSON-Schema snapshots · `npm ci --ignore-scripts`, `npm audit signatures`,
the npm licence check, `tsc`, `vitest` · the Playwright security contract against a debug
binary · a reported (non-gating) `criterion` smoke run.

Mutation testing, fuzzing, full-history gitleaks, the full-history container-magic scan
(`cargo xtask check-magic --history` — gitleaks cannot see the magic in history, because git
diffs a file containing a NUL as binary), oracle re-recording, cross-architecture
determinism and the gating benchmark run nightly, not per push (`TESTING.md` §11.1 stage 2).

### 7.4 Merge gates a contributor acts on (`TESTING.md` §11.2)

1. Stage 1 green.
2. **Tier 1 at 100%: no tolerance, no skips.**
3. Tier 2 skip count no higher than the baseline in the validation report.
4. A tier-3 golden change carries an `engineVersion` bump and a reviewed diff.
5. **New engine behaviour arrives with its fixtures in the same PR.** No feature merges
   without them.
6. Touched money, tax or Social Security crates meet the surviving-mutant budget; touched
   parsers meet the fuzz budget.
7. No new `f64` beyond the two named entries, no new dollar literal in an engine crate, no new
   `std::fs`, `std::net` or HTTP-client dependency outside its permitted crate.
8. A threat-model delta is reviewed if any row of `ARCHITECTURE.md` §8 changes.
9. A new parameter table meets §1.3 and §3.2 in full.
10. A changed public parameter value ships as a new vintage.

### 7.5 Commit messages

Describe the change and why, cite the design section it implements, and keep it
user-agnostic (§3.5). A port or transliteration mentions its `NOTICE` entry, which is in the
same commit.

## 8. Open design decisions awaiting an ADR

The scaffold met four places where the design documents leave a contradiction or a gap that
configuration cannot honestly settle. Each is recorded here — and pointed at from the file it
affects — so that it is closed by an ADR in [`DECISIONS.md`](DECISIONS.md) *before* the pull
request that depends on it, not inside it. Remove an item when its ADR lands.

1. **`ring` and the OpenSSL licence (blocks the `rustls` pull request).** `SECURITY.md` §11
   asks for the `ring` licence clarification to be pre-declared at M0. An honest clarification
   records `MIT AND ISC AND OpenSSL`, and `OpenSSL` is not one of the eight permitted
   licences; the same section forbids a clarification that records what the project wishes a
   licence were, and says the permitted set is extended only by ADR. `deny.toml` therefore
   declares no clarification. Needed: an ADR that either admits `OpenSSL` for `ring`
   specifically, or selects a TLS crypto provider whose licence is already permitted.
2. **Build-time-only front-end dependencies (ADR-002, ADR-004).** `@vitejs/plugin-react` is not
   installed (its Babel path pulls `caniuse-lite`, CC-BY-4.0) and Vite is held at 7.x (Vite 8
   hard-depends on `lightningcss`, MPL-2.0). Both packages are build-time only and never reach
   a shipped artifact. Needed: an ADR — an ADR-002 amendment or a new one — deciding whether
   the eight-licence set governs build-time-only packages at all. Until it exists the hold is
   enforced by the `vite` rule in `renovate.json` and explained in `web/README.md`.
3. **Pre-commit clippy (`TESTING.md` §11.1 stage 0).** See §7.2: clippy is implemented at
   pre-push. Needed: either the stage-0 list is amended, or a changed-crates clippy invocation
   fast enough for a commit hook is specified.
4. **The rest of the §13.4 pattern check (`SECURITY.md` §14 places it at M0).** Three parts of
   the check are not built: the real-looking email and street-address rule for fixtures, the
   passphrase-flag and `env::var` lint over `pfp-app`, and a nightly full-history sweep of the
   SSN, plan-shaped-JSON and `asOf` rules (§1.5). None can fire on the scaffold — there is no
   `fixtures/` directory and `pfp-app` has no command line — so nothing is unprotected today;
   this is a schedule item rather than a design gap. Needed: the first two land in the pull
   requests that create `fixtures/` and the `pfp-app` CLI respectively, and must not be
   deferred past them; the history sweep needs a `data-hygiene --history` mode alongside
   `check-magic --history` in `nightly.yml`. No ADR is required unless "real-looking" needs a
   definition that `SECURITY.md` does not give.

## 9. Nothing in this repository is financial advice

The application models tax and planning rules from published sources. Fixtures, examples and
documentation use synthetic figures throughout, and a synthetic figure is never a
recommendation.
